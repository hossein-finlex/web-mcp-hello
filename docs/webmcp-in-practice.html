WebMCP in Practice

An assistant inside your own web app has a specific problem: it has no idea what your app can do. WebMCP lets the page answer that question itself — by registering its capabilities as callable tools instead of leaving the agent to infer them from the rendering.

The problem

Chat is not the hard part

Putting a chat panel in a web app is easy. Making it do anything is where it falls apart, and it falls apart in two predictable directions.

It describes instead of acting
The assistant can read your data but cannot touch the app, so it hands the work back to the user as instructions. "Contract FL-0142 expires in 42 days. Open it and click Renew to extend the term."
It acts blindly
Given the DOM and a mandate, it guesses. It clicks the third row because the third row was right last week. When it fails you get a stack trace about a missing element, not a reason. Error: no element matches .row:nth-child(3) button

Both failures share one root cause. A language model shown a rendered page sees markup or pixels — neither of which expresses what the application can do. Capability and intent are exactly the things a rendering throws away.

What we actually needed

Discoverable The assistant learns what the app can do at runtime, from the app — not from a prompt someone remembered to update.
Visible When it acts, the screen changes while the user watches. A renewal that happens silently in a database is indistinguishable from a lie.
Legible Failures come back as reasons, not selector errors: "no contract with id FL-9999 — call search_contracts for valid ids".
Durable A redesign changes markup. It must not change the contract between the app and the assistant.
Supervised Consequential work pauses for a human. The assistant may prepare a bulk renewal; a person commits it.
The solution

Let the page declare itself

MCP — the Model Context Protocol — is a standard way for a model to discover tools and call them by name. WebMCP is that idea moved inside the browser tab: a page exposes its own capabilities through navigator.modelContext, and any agent with access to the page can list them and invoke them.

The inversion is the whole point. Instead of the agent inferring what it can do from what it can see, the application states what it can do.

What a registered tool looks like

A tool is four things: a name, a description the model reads to decide when to use it, a JSON Schema for its arguments, and a function. In our app the function is an ordinary React handler — which is why calling it moves the UI. 

registerTool({
  name: 'renew_contract',
  description:
    'Renew a contract: the new term starts the day the old one ends, so cover
     stays continuous. Leave premium and sum_insured alone unless the user
     asked to change them. Clears the renewal_pending flag.',
  inputSchema: {
    type: 'object',
    properties: {
      contract_id: { type: 'string' },
      months:      { type: 'integer', description: 'Defaults to 12.' },
    },
    required: ['contract_id'],
  },
  async execute({ contract_id, months = 12 }) {
    const renewed = await api.renewContract(contract_id, { months });

    setRoute({ view: 'contract', contractId: contract_id });  // the view moves
    flash(contract_id);                                       // the row pulses

    return toolResult({ ok: true, contract: renewed });
  },
});
Why the description matters more than it looks

That paragraph of prose is not documentation for humans — it is the only thing the model reads when deciding whether this tool fits the request. Ours tells it the term rolls from the current expiry, and not to touch pricing uninvited. Tool descriptions are prompt engineering, and they live next to the code they describe.

The surface

CallWho uses itWhat it does
registerTool(descriptor) the page Publishes one capability. Returns a handle with unregister().
unregisterTool(name) the page Withdraws it — a tool that is not currently valid should not be listed.
provideContext({ tools }) the page Replaces the whole set at once, for pages that rebuild it wholesale.
listTools() the agent Reads names, descriptions and schemas. Never the implementations.
callTool(name, args) the agent Invokes one and awaits an MCP-shaped result.

The first three are the page's half and are what the proposal specifies. The last two are the agent's half — and today, in a browser without native support, you supply both. Ours lives in a polyfill that stubs the page-side API and keeps a mirror of the registry so the agent-side calls work either way.

Why the tool list is re-sent every message

Step 1 looks wasteful and is not. The registered set genuinely changes as the user navigates — a tool that only makes sense on the detail view is registered when that view mounts and withdrawn when it unmounts. Re-sending the list is how the model finds out. That is dynamic capability discovery, and it is the reason registration is a lifecycle concern rather than a config file.

The other half

Work that has no business in a UI

Not everything should be driven through the page. Renewing fourteen contracts by calling a page tool fourteen times is fourteen round-trips through the model, any of which can stop halfway and leave the book half-renewed. Assembling a report is computation, not clicking. Market benchmark rates live outside the application entirely.

So those became server tools: they run in the backend, in one transaction, and never touch the browser. Which creates a new problem — server work is invisible. The fix is the pattern below.

Implementation note

The trap that costs everyone a day

Registration looks like a mount-time concern, so the obvious code is an effect with an empty dependency array. That is wrong in a way that does not announce itself: the handler closes over the state that existed at mount, and keeps returning it forever.

Wrong — silently stale
useEffect(() => {
  const handle = registerTool({
    name: 'search_contracts',
    execute: () => filter(contracts),   // frozen at mount, forever
  });
  return () => handle.unregister();
}, []);
Also wrong — churns the registry
useEffect(() => {
  /* … same registration … */
}, [contracts]);   // re-registers on every keystroke; an
                 in-flight call can be pulled out from
                 under the agent mid-execution
Right — stable registration, fresh handler
const latest = useRef(tools);
latest.current = tools;              // refreshed every render

useEffect(() => {
  const handles = latest.current.map(({ name, description, inputSchema }) =>
    registerTool({
      name, description, inputSchema,
      // late-bound: resolve the handler at call time, not register time
      execute: (args) => latest.current.find((t) => t.name === name).execute(args),
    })
  );
  return () => handles.forEach((h) => h.unregister());
}, []);   // registration really is mount-only — the indirection does the rest

Register once, resolve late. Names and schemas are static; handlers are re-created every render and always see current state. Under React StrictMode's double-mount you can verify it by counting: exactly ten tools registered, not twenty and not zero.

The honest summary

Of the ten tools we registered in the page, four jobs genuinely required it: navigation, form prefill, making view state visible, and delivering server artifacts to the screen. The reads and writes could all have been server tools. WebMCP earns its keep on UI state, not on data state — and that is the most useful thing this POC established.

Status. WebMCP is a proposal; native navigator.modelContext is not something to rely on yet. This POC ships a polyfill that stubs the page-side API when it is absent and logs every registration and invocation to the console, so the app behaves identically either way and the header badge tells you which one you got.

Scope. Everything described here runs: tool registration and its lifecycle, JSON Schema declarations, discovery, invocation, MCP result and error shapes, and the routing of each call to the browser or the backend.
